# FuseMoE Migraine Prediction System: Implementation Documentation

## 1. Introduction

This document details the implementation of a migraine prediction system utilizing the FuseMoE (Fused Mixture-of-Experts) architecture. The goal is to predict the likelihood of a migraine occurring on the next day based on multimodal data, potentially combining Electronic Health Record (EHR) data structures (inspired by MIMIC-IV or generated by Synthea) with synthetic data representing specific expert modalities: sleep patterns, weather conditions, stress/diet factors, and physiological signals.

The system leverages the FuseMoE framework to allow specialized expert networks to process data from different modalities, with a gating network determining the contribution of each expert for a given input.

## 2. Data Sources and Structure

The system is designed to be flexible and can work with:

*   **EHR Data (MIMIC-IV/Synthea):** Provides patient demographics, diagnoses (ICD codes), procedures, prescriptions, lab results (`labevents`), vital signs (`chartevents`), and clinical notes (`noteevents`). Requires access and significant preprocessing.
*   **Synthetic Generators:** Python scripts (`patient_profile_generator.py`, `sleep_data_generator.py`, `weather_data_generator.py`, `stress_diet_generator.py`, `migraine_event_generator.py`) create structured CSV files simulating patient data and migraine events.
*   **External Weather Data:** Historical weather data (temperature, humidity, pressure) for the relevant location needs to be obtained separately.

The `data_processor.py` script handles the loading, merging, and preprocessing of these diverse sources.

## 3. Data Preprocessing (`data_processor.py`)

This script performs the following key steps:

1.  **Loading:** Loads data from CSV files generated by the synthetic generators (or potentially from MIMIC-IV/Synthea database/files).
2.  **Feature Engineering:** 
    *   Calculates weather changes (e.g., pressure change over 24h).
    *   Normalizes continuous features (sleep metrics, weather data, stress level, water consumed) using Min-Max scaling.
    *   Converts boolean flags (dietary triggers) to integers.
    *   Handles potential missing columns (e.g., checks for 'sex' before encoding).
3.  **Merging:** Creates a master index of patient-date combinations and merges features from different sources based on patient ID and date.
4.  **Target Variable Creation:** Generates the binary target variable (`migraine_next_day`) by shifting the migraine occurrence data (from `migraine_event_generator.py` or derived from EHR data) by one day.
5.  **Handling Missing Values:** Fills remaining NaNs, typically using forward fill or filling with 0 after merging.
6.  **Data Splitting:** Splits the final dataset into training, validation, and test sets based on predefined dates to prevent temporal data leakage.
7.  **Output:** Returns Pandas DataFrames for training, validation, and testing features (`X`) and Series for the corresponding targets (`y`).

## 4. Model Architecture (`updated_fusemoe_integration.py`)

*   **`FuseMoEMigraineModel`:** The core PyTorch model class.
    *   Takes a configuration dictionary defining dimensions (`model_dim`, `hidden_dim`, modality dimensions like `sleep_dim`, `weather_dim`, etc.) and MoE parameters (`num_experts`, `k`).
    *   Contains separate expert networks (`nn.Sequential` layers) for each modality (Sleep, Weather, Stress/Diet, Physio).
    *   Utilizes modified FuseMoE layers (`HierarchicalMoE` from `hme_seq.py`) as the gating network and potentially for combining expert outputs (though the current implementation uses a simple linear layer for final prediction).
    *   The `forward` pass takes keyword arguments corresponding to the feature groups created by the adapter (`sleep_features`, `weather_features`, etc.) and processes them through the respective experts and gating mechanism.
*   **`FuseMoEAdapter`:** A helper class responsible for:
    *   Taking the DataFrame output from `data_processor.py`.
    *   Splitting the features into groups corresponding to the expert modalities based on predefined column names.
    *   Converting these groups into PyTorch tensors.
    *   Handling the placeholder for physio data if it's not present, ensuring it has the correct dimension (`physio_dim_expected`).
    *   Returning a dictionary of feature tensors and a tensor for the targets, ready for the `MigraineDataset` and `DataLoader`.
*   **Configuration (`create_fusemoe_model`)**: Helper function to instantiate the model with a specific configuration.

## 5. FuseMoE Library Modifications

Significant modifications were required to make the original FuseMoE library (designed for PyTorch 1.7.1) compatible with our environment (PyTorch 2.7.0) and data structure:

*   **`sparse_moe.py`:**
    *   Corrected import alias for `MoE` class.
    *   Modified `create_sparse_moe_layer` in the integration module to pass `MoEConfig` instead of individual arguments.
    *   Changed `router_type` to "joint" in `MoEConfig` within the integration module to fix tensor dimension issues related to modality handling.
*   **`hme_seq.py`:**
    *   Corrected import name from `HierarchicalMoE_seq` to `HierarchicalMoE` in the integration module.
    *   Modified `HierarchicalMoE.__init__` to properly initialize `self.w_gate` and `self.w_noise` as persistent `nn.ParameterList`.
    *   Updated `_get_logits` to use these class attributes and handle potential unassignment of `clean_logits`.
    *   Corrected the `gating` parameter in `MoEConfig` (within the integration module) to be a list (e.g., `["softmax", "softmax"]`) instead of a string.
    *   Replaced the complex `SparseDispatcher` logic within `hme_seq.py` with the simpler, more robust version from `sparse_moe.py` to resolve `torch.gather` errors related to batch indexing and dimension mismatches.

## 6. Training and Evaluation (`train_evaluate.py`)

This script orchestrates the training and evaluation:

1.  **Data Loading:** Calls `process_data()` from `data_processor.py`.
2.  **Model & Adapter Instantiation:** Creates the `FuseMoEMigraineModel` and `FuseMoEAdapter` using a defined configuration.
3.  **Data Adaptation:** Uses the adapter to convert the DataFrames into tensor dictionaries.
4.  **Dataset & DataLoader:** Wraps the adapted data using the custom `MigraineDataset` and PyTorch `DataLoader` for batching.
5.  **Training Loop (`train_model`):** 
    *   Iterates over epochs and batches.
    *   Performs forward pass, calculates Binary Cross-Entropy loss, performs backward pass, and updates weights using the Adam optimizer.
    *   Includes a validation loop after each epoch to monitor performance on unseen data.
6.  **Evaluation (`evaluate_model`):**
    *   Runs the trained model on the test set.
    *   Calculates Accuracy, Precision, Recall, F1-Score, and ROC-AUC.
    *   Prints the results.

## 8. Usage Instructions

1.  **Generate Data:** Ensure synthetic data CSVs are present (e.g., by running `synthetic_data_generator.py` in the `/home/ubuntu/` directory, assuming all generator scripts are copied there) or configure `data_processor.py` to load MIMIC-IV/Synthea data.
2.  **Train & Evaluate:** Run `python3 /home/ubuntu/train_evaluate.py`. This will process the data, train the model, and evaluate it. *(Note: Training is currently in progress)*. Upon completion, it should save `evaluation_results.json`.
3.  **View Dashboard:** Once training is complete and `evaluation_results.json` exists, run `streamlit run /home/ubuntu/dashboard.py` in the terminal. Access the provided URL in your browser.

## 9. Limitations and Future Work

*   **Synthetic Data:** The current evaluation relies on synthetic data. Performance on real-world EHR data (MIMIC-IV/Synthea) may differ significantly.
*   **Physio Data:** The physio modality currently uses placeholders. Integrating real physiological signals from `chartevents` or other sources would be a major enhancement.
*   **Feature Engineering:** More sophisticated feature engineering, especially for clinical notes (NLP) and time-series data, could improve performance.
*   **Hyperparameter Tuning:** The current model uses default hyperparameters. Tuning (learning rate, batch size, model dimensions, MoE parameters) is recommended.
*   **Expert Contribution Analysis:** The dashboard currently lacks visualizations for expert contributions. Modifying the model to output gating weights during inference would enable this.
*   **Scalability:** Training on the full MIMIC-IV dataset would require significant computational resources.
